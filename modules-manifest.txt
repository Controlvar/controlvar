# modules-manifest.txt — the optional modules' file list.
#
# FORMAT
#   One repository-relative path per line, as the file sits in the tree: the
#   modules live under `modules/` (issue #89), mirrored from where they were
#   written -- `backend/app/x` is `modules/backend/app/x`, `backend/tests/x` is
#   `modules/backend/tests/x`, `backend/lambda/x` is `modules/lambda/x`,
#   `infrastructure/x` is `modules/infrastructure/x`. A path may be a file or a
#   directory; a directory entry covers everything under it. Blank lines and
#   lines starting with "#" are ignored.
#   The boundary test derives both spellings of every module name from these
#   paths -- `modules.backend.app.x` and the pre-move `backend.app.x` -- so a
#   core file that reaches for either is a crossing.
#
# WHO READS IT
#   backend/tests/smoke/test_core_boundary.py (P1) AST-walks
#   backend/{app,scripts,lambda,tests} and fails on:
#     * any import of a module named here,
#     * any string literal naming one (patch() targets, monkeypatch.setattr,
#       dotted-path settings) — NOTE: resolve module-level string constants,
#       not just literal call arguments. backend/tests/integration/api/
#       test_hipaa_api.py makes 38 patch() calls through class constants
#       (_SVC_CREATE etc.); only 13 are literal arguments.
#     * Base.metadata.tables intersecting MODULE_TABLES (listed at the bottom).
#   scripts/core_build.sh deletes `modules/` whole and must still get a green
#     `import backend.app.main`, a core-only bootstrap and green pytest. "Green
#     pytest" means: every test that survives the deletion passes, with the
#     tests marked `@pytest.mark.modules` skipped — those live in files that
#     are otherwise core but exercise a module's behaviour (a module route
#     answering, the signer signing, the wiring of module routers).
#     backend/tests/conftest.py skips the marker when the modules did not load.
#
# HOW ENTRIES WERE DECIDED
#   Two tests, both answered from the code, not from the plan's table:
#     (1) does the core still work with the module deleted?
#     (2) does anything that stays in the core import it?
#   Where (2) is non-zero the entry carries the crossing that must be cut
#   first, as the pre-move coupling analysis established.
#
# The group numbers 1..10 are the ten module names (`hooks.KNOWN_MODULES`,
# in this order: workspaces, hipaa, compliance, sso, rbac, warehouse,
# integrations, counters, etl, split_url); 11 is the dashboard's
# implementation directory and 12 the registration.

# =============================================================================
# DELIBERATELY NOT IN THIS MANIFEST — recommendations, with reasons
# =============================================================================
#
# MUTUAL EXCLUSION GROUPS + GLOBAL HOLDOUT → keep core (recommendation).
#   The plan's own §3 table already says core and §2 says "MEG/bandit stay
#   core"; only the task brief lists them as a module. Keep them core.
#   Evidence beyond the commercial "table stakes" argument: they are on the
#   assignment hot path — assignment_service.py:21-22 imports both services
#   at module level and assign_user calls them for every new user. Moving
#   them turns the single most-exercised core code path into a brokered call
#   with two fallbacks, and models/experiment.py:170 keeps a
#   relationship("MutualExclusionGroup") that would then need the same FK
#   surgery as workspace_id. Cost: high. Benefit: none now that every module
#   is free.
#
# BAYESIAN + CUPED → keep core (recommendation).
#   Plan §3 says core; the task brief says module. Keep core. They are not
#   bolt-ons: schemas/results.py:17 types the main results response with
#   BayesianResultsResponse, analysis_service.py:19,26 computes it inside the
#   standard results path, results.py:438 returns it on GET /results/{id},
#   and results.py:46 imports CupedService. Making them a module means the
#   core results response changes shape by profile — the OpenAPI stable
#   snapshot (P2) then cannot be one document. The statistics are also the
#   product's credibility argument at launch; they are the wrong thing to
#   make optional.
#
# BANDITS → keep core. main.py:18 starts bandit_scheduler_runner in the
#   lifespan, tracking.py:20 reads BanditState on every /tracking/assign,
#   analysis_snapshot_service.py:283 writes BanditStateHistory. Three hot-path
#   crossings for a feature the plan already calls core.
#
# INTERACTIONS, WEBSOCKET LIVE RESULTS, AI DESIGN + MCP →
#   keep core, as the plan's §3 table says. Each is self-contained (no core
#   importer outside models/__init__.py and api.py), so they could move
#   cheaply — but nothing is gained: none is a thing a buyer asks for. (The
#   edge bootstrap route once listed here was removed, #737; the edge SDK
#   calls the evaluate, user-flags and tracking routes.)
#
# LLM / AI MODEL EVALUATION (EP-046) → undecided; the plan's profile table
#   omits it entirely. It is self-contained (3 tables, one crossing at
#   models/__init__.py:32) and, like warehouse and integrations, has never
#   been run against a live provider. Recommendation: a module, same
#   "roadmap, not marketed" bucket as warehouse — but decide explicitly
#   rather than letting it default to core by omission.
